# /design shape -- Design Brief Through Discovery

Before anyone writes code, shape the feature. Run a structured discovery conversation about purpose, users, content, and constraints, then capture the answers as a design brief.

The brief is the output. No code. No pixels. Just clarity.

---

## Workflow

### Step 1: Load Context

Before asking anything, gather what already exists:

1. **PRODUCT.md** (project root): Pull register, users, brand personality, anti-references. Pre-fill anything the user already answered.
2. **DESIGN.md** (project root): Note the visual system, tokens, constraints already in play.
3. **Codebase signals**: Existing components, routes, patterns relevant to the feature being shaped.

If PRODUCT.md exists, you should already know who the users are and what the product does. Don't re-ask what's answered. Reference it and build on it.

If neither file exists, note the gap and proceed. The interview still works; it just can't lean on established context.

---

### Step 2: Run the Discovery Interview

This is a **conversation**, not a form. Ask, listen, follow up. Adapt based on what you learn. The goal is to understand the feature deeply enough that any designer could build it from the brief alone.

Four threads to pull on, in this order:

#### Thread 1: Purpose and Context

> "What is this feature for? What problem does it solve, and for whom?"

Follow-ups to dig deeper:

- What triggers the user to need this? What were they doing right before?
- What state of mind are they in? Rushed, browsing, anxious, focused?
- What does success look like? If the feature works perfectly, what happens next?
- Is this a daily-use feature or a once-in-a-while interaction?

Reference PRODUCT.md users if available: "Your users are [X]. Is this feature for all of them, or a specific segment?"

#### Thread 2: Content and Data

> "What is actually shown on this screen? Walk me through what the user sees."

Follow-ups:

- What content is dynamic vs. static? What changes per user, per session, per context?
- What are realistic data ranges? Minimum, typical, maximum. (A list with 3 items behaves differently than a list with 300.)
- What are the edge cases? Empty state, error state, overflow, missing data, first-time use.
- Does content come from the user, from the system, or from a third party?
- Are there images, media, or rich content involved?

Push for specifics. "A list of items" is not enough. "A list of 5-50 task cards, each with a title (max 80 chars), status badge, assignee avatar, and due date" is.

#### Thread 3: Design Goals

> "If this feature could only do one thing perfectly, what would it be?"

Follow-ups:

- What should the user _feel_ when they use this? Confident? Delighted? Efficient? Reassured?
- Are there reference examples, either from this product or others, that capture the right feeling?
- What's the hierarchy of importance? If you had to rank the elements on screen, what comes first?
- Is speed/efficiency the priority, or is this a moment to slow down and guide?

#### Thread 4: Constraints

> "What limits are we working within?"

Follow-ups:

- Technical constraints: framework, component library, existing patterns to match, performance budget
- Content constraints: localization, dynamic text length, user-generated content
- Accessibility constraints: specific WCAG level, known user needs, assistive technology support
- Scope constraints: is this a v1 or a polish pass? What's explicitly out of scope?
- Platform constraints: desktop only, mobile-first, responsive, touch targets needed?

**Interview style notes:**

- This should feel like a design lead asking the right questions, not a requirements doc.
- Follow up on interesting answers. If someone says "The user is stressed," ask what kind of stressed and what would calm them down.
- Reference what you already know from PRODUCT.md and the codebase. "I see you're using shadcn cards for similar lists. Should this follow the same pattern?"
- If an answer is vague, push once. If still vague, note it as an open question in the brief.
- You don't need to ask every question. If the feature is straightforward, a shorter interview is fine. Use judgment.

---

### Step 3: Produce the Design Brief

After the interview, synthesize into a brief. Write it to `brief.md` in the relevant directory, or present inline if the user prefers.

```markdown
# Design Brief: [Feature Name]

> Generated by /design shape. Hand to /design craft, /design, or any implementation flow.

## Purpose

[What this feature does and why it exists. One to two sentences.]

## User

[Who uses this, their mental state, their context. What they were doing before they arrived here and what they'll do after.]

## Content

[What's displayed. Dynamic vs. static. Realistic data ranges. Edge cases (empty, error, overflow, first-time).]

## Feeling

[The intended emotional response. How the user should feel during and after using this feature.]

## Constraints

[Technical, accessibility, content, platform, scope limits. What's explicitly out of scope for v1.]

## Hierarchy

[Priority order of elements. What matters most, second, third. What can be de-emphasized or hidden.]

## Recommended References

[Which reference files from {SKILLS_PATH}/design/_references/ are relevant:]

- spatial-design.md (always)
- typography.md (always)
- [Others as needed: motion-design.md, color-and-contrast.md, interaction-design.md, responsive-design.md, ux-writing.md]

## Open Questions

[Anything that came up during discovery but wasn't resolved. Flag these for the builder.]
```

**Brief writing guidelines:**

- Keep each section to 2-5 sentences. Dense, not verbose.
- Use the user's own words where it captures intent better than a polished rewrite.
- Content section must include specific data ranges and edge cases, not hand-waves.
- Recommended References should be selective. Don't load all 7 unless the feature genuinely spans all 7 dimensions.
- Open Questions section is mandatory. If there are no open questions, say "None." But there almost always are.

---

### Step 4: Confirm and Hand Off

Present the brief. Ask if anything is wrong or missing.

Once confirmed, offer the next step:

> "Brief is locked. Want me to run `/design craft` to build this, or are you handing this to someone else?"

---

## Rules

1. **The brief is the output.** Do not write code, generate components, or produce visual designs. Shape produces clarity, not pixels.
2. **The interview is a conversation.** Never dump all questions at once. Ask, listen, follow up, adapt.
3. **Pre-fill from PRODUCT.md.** If the user already told you who their users are in PRODUCT.md, don't ask again. Reference it and build on it.
4. **Push for specifics on content.** Vague content descriptions produce vague designs. Data ranges, character limits, and edge cases matter more than most people think.
5. **Every section of the brief must trace to something the user said.** Don't invent constraints or assume feelings. If you don't know, put it in Open Questions.
6. **Recommended References should be justified.** Don't recommend motion-design.md for a static data table. Match references to actual feature needs.
7. **Keep it brief.** The design brief should fit on one screen. If it's longer, you're over-specifying. The builder needs direction, not a novel.
